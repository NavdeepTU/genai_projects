Feature 24 — Streamed answer generation Complete

A real security trade-off, named not hidden: the injection judge needs the complete answer to judge whether retrieved document text hijacked it, so it can only run once every sentence has already streamed — a flagged answer is retracted (the client erases what it showed), not prevented from ever appearing. Multi-domain questions get none of the streaming benefit at all: each domain still fully generates its own draft, and the merged answer arrives as one piece.

A /code-review pass found six real, confirmed issues after the initial build, all fixed the same session: unguarded audit-log calls inside the SSE generator that could silently truncate the stream on a DB failure; duration_ms measuring a different span of work than /query's own definition, which would have skewed the Analytics page's average-response-time metric; raw dicts instead of Pydantic models for the SSE payloads; a missing docstring and return type on the core generator function; a FederatedResult.duration_ms silently left unset, breaking another method's own stated contract; and a fully dead non-streaming code path (postQuery, its proxy route) left behind once nothing called it.

Verified live, twice: a real streamed answer through the browser (network inspection confirmed the request stayed genuinely pending, not resolved instantly), and — unplanned but useful — a real block via the injection guardrail against a test document already in the corpus, confirming both the successful and the blocked answer saved correctly through the streaming path. Verified again after the /code-review fixes. Backend suite: 94 → 108 passing · frontend suite: 17 → 26 passing. See ADR-043.

Feature 25 — Viewing a document, and Blob Storage Complete

first time this project persists an uploaded file's original bytes, not just its extracted text
Built app/core/blob_storage.py Azurite locally · Managed Identity (no key at all) in production
Built Saved at upload, synchronously best-effort — a failed save never fails the upload itself
Built GET /documents/{id}/content same permission check as everything else · renders inline

A real, newly-introduced gap found by rereading the architecture notes, not by being told: a document flagged for PII review used to have its file discarded along with everything else. It's now saved before the PII check even runs — so a flagged document's original file, PII and all, is viewable by anyone with access, even while the document sits "held for review." Not fixed this session — the content route checks access, not status.

Priced out before committing, not assumed: at this project's actual document volume, Blob Storage costs a few cents a month at most. Local development uses Azurite (Docker, free) rather than the real account, matching how Postgres, Neo4j, and Redis already work locally in this project.

Verified live: existing documents (uploaded before this feature) correctly show "Not viewable"; a freshly uploaded document's "View" link was confirmed to serve the real file — fetched from Azurite through the new route and proxy, rendered inline with the correct content type — and the database's storage_path column was checked directly against the actual blob name written. Backend suite: 108 → 119 passing · frontend suite: 26 → 28 passing. See ADR-044.

Feature 26 — Deleting a document, completely Complete

removes a document from all three places this project now stores something about it
Built Confirmation dialog Shadcn AlertDialog — first real confirm-before-destroy UI in this project
Built DocumentDeletionService blob + graph delete best-effort · database delete must succeed
Built Cascade delete chunks + permission grants — zero orphans, checked directly

Two real bugs caught before/after shipping: AsyncSession.delete() is itself a coroutine in SQLAlchemy's async ORM — the first version called it without await, silently doing nothing beyond a buried RuntimeWarning, caught by the cascade-delete test actually checking the row was gone. Separately, a user-reported bug: CardHeader is a CSS Grid container, and a grid item defaults to min-width: auto just like a flex item — the header row was never actually constrained to the card's width, so a long filename could push the delete button off the visible card. Fixed with one min-w-0, reproduced with a matching long filename before trusting the fix.

No new ownership concept, on purpose: anyone with access can delete a document today, the same has_access rule sharing already uses — building a real "owner" concept to protect a multi-user scenario with no UI and no real usage would have been speculative scope.

Verified live: a real document deleted through the actual confirmation dialog, then checked directly — zero orphaned rows in chunks or document_permissions across the whole database, the blob actually gone from Azurite (container contents listed before and after), and the audit log entry carrying the correct deleting user_id. Backend suite: 119 → 133 passing · frontend suite: 28 → 33 passing. See ADR-045.

Feature 27 — Multi-tenancy Complete

tenant-wide document sharing replaces the old per-user grant table; conversations stay per-user
Built Tenant model + repository GET /tenants (public) · POST /admin/tenants (require_admin)
Built tenant_id replaces document_permissions DocumentPermission + PermissionRepository deleted outright
Built Two cross-tenant leak fixes Neo4j reference-graph scoping · MCP X-User-Id now DB-verified

A real, named tension with this project's own Enterprise Requirement 5: "multi-tenancy is not enough — users should only retrieve chunks from documents they have explicit access to." As built, tenant membership is the whole of document access control — every user in a tenant can read every document that tenant owns, with no remaining per-document restriction. A deliberate trade-off for this feature's stated scope, not an oversight, recorded plainly in ADR-046 rather than smoothed over.

Two real bugs caught by /code-review, both fixed the same session: two concurrent requests to register the same tenant name could both pass the pre-check and the second would surface an unhandled 500 instead of a 409 — fixed by catching the underlying IntegrityError. A tenant name with leading/trailing whitespace could bypass the duplicate-name check entirely — fixed with a Pydantic validator on the request model itself, not just the one frontend form that exposed it.

Verified live: two independent users signed up into the same tenant, one instantly saw a document the other had just uploaded, with zero grant. A second tenant registered, a third user signed into it landed at zero documents, and a question answerable only from the first tenant's data came back "I don't know" — confirming isolation holds at retrieval, not just in the document list. Backend suite: 133 → 150 passing · frontend suite: 37 passing (restructured, not added to). See ADR-046.
